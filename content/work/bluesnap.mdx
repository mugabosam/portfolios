## Context

On a campus, at an event or anywhere with poor connectivity, mobile data is expensive or simply absent, yet the people you want to reach are often a few meters away. BlueSnap brings the familiar parts of a social app (a feed, stories and direct messages) to phones in the same place, with no internet at all. Your identity, messages and media live only on your device.

## My role

I built it alone: the transport layer, the encryption, local storage and the interface.

- **One real transport.** Google Nearby Connections handles Bluetooth Low Energy discovery and upgrades to Wi-Fi for throughput. I settled on that single transport rather than maintaining several half-working ones.
- **Trust on first use.** Peer keys are pinned on first contact, and a changed key raises a warning instead of being trusted silently. Incoming connections need explicit approval, and every chat shows a safety-code fingerprint that two people can compare in person.
- **Keys stay in hardware.** The private identity seed lives in the Android Keystore, never in plaintext, and app backups are disabled.
- **Messages wait for people.** If a friend is out of range, the message is queued and delivered the next time their phone connects.

Version 1 targets Android only. Nearby Connections has no iOS SDK; iOS would need Apple's MultipeerConnectivity instead.

```dart
/// Encrypt [plaintext] for [peerPublicKeyB64].
/// Returns base64(nonce ++ ciphertext ++ mac), or null if no session.
Future<String?> encryptFor(String peerPublicKeyB64, String plaintext) async {
  final key = await _sessionKey(peerPublicKeyB64);
  if (key == null) return null;
  final box = await _aes.encrypt(
    utf8.encode(plaintext),
    secretKey: key,
  );
  return base64.encode(box.concatenation());
}
```

</Snippet>

Each device has a long-lived X25519 identity key. Two devices derive the same shared secret, and HKDF-SHA256 stretches it into an AES-256 key. AES-GCM authenticates as well as encrypts, so a tampered message fails to decrypt instead of producing garbage.

### Forward secrecy per connection

</Snippet>

Identity keys alone mean a stolen key could decrypt old conversations. Each connection therefore also runs an ephemeral handshake that mixes both phones' identity keys with fresh one-time keys, the same shape as Noise-IK and X3DH. The one-time keys live only in memory and are wiped when the session ends. The tricky part is order: both phones must combine the three secrets in the same order, so the code assigns roles by comparing the two public keys instead of trusting who connected first.

Messages are keyed by a stable ID from the moment they are written. Retries can then happen as often as needed: the receiver acknowledges by ID and discards anything it has already seen.

## Results

The results are engineering ones. Static analysis reports zero errors, and unit tests cover the crypto, the wire protocol, the message queue and safety checks.

BlueSnap is built privacy-first, but it has not been formally audited, and I don't describe it as secure until someone independent has tried to break it.

## What I'd do next

- **An independent security review.** Encryption code deserves eyes that did not write it.
- **iOS** through MultipeerConnectivity, behind the same transport interface.
- **Multi-hop relay**, so a message can pass through other phones to reach someone out of direct range. It is not built today.
