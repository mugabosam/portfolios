## Context

Inventory Pro is one of my earlier projects, from March 2025: a web application for tracking products, suppliers and stock across several storage locations. It is where I learned to model a real domain in Django and to turn database rows into documents people can actually use.

## My role

I built it alone: the data model, the views and templates, authentication and the reporting.

- **Generic views for the routine parts.** Listing, creating, editing and deleting products, categories and suppliers all use Django's class-based views, which keeps the code for each screen short.
- **Stock moves are records, not edits.** Purchases, sales and adjustments are stored as transactions with a type, quantity and notes, so the history of each product can be reconstructed.
- **Nested categories.** A category can have a parent category, so the catalog can grow without a schema change.
- **Accountability.** Every login attempt and registration is logged with a timestamp, the IP address and the user agent.

### The core of the data model

```python
class Product(models.Model):
    name = models.CharField(max_length=100)
    category = models.ForeignKey(Category, on_delete=models.SET_NULL, null=True)
    supplier = models.ForeignKey(Supplier, on_delete=models.SET_NULL, null=True)
    quantity_in_stock = models.IntegerField(default=0)
    price = models.DecimalField(max_digits=10, decimal_places=2)
    ...
    def is_low_stock(self):
        return self.quantity_in_stock < 10  # Adjust threshold as needed


class InventoryTransaction(models.Model):
    TRANSACTION_TYPES = [
        ('PURCHASE', 'Purchase'),
        ('SALE', 'Sale'),
        ('ADJUSTMENT', 'Adjustment'),
    ]

    product = models.ForeignKey(Product, on_delete=models.CASCADE)
    transaction_type = models.CharField(max_length=20, choices=TRANSACTION_TYPES)
    quantity = models.IntegerField()
    timestamp = models.DateTimeField(auto_now_add=True)
    ...
```

</Snippet>

Deleting a category or supplier sets the product's reference to null instead of deleting the product. Prices are decimals, never floats, so money adds up exactly.

### One exporter, many reports

```python
    def get(self, request, report_type, format):
        ...
        if format == 'csv':
            return self.generate_csv(queryset, report_config, filename)
        elif format == 'excel':
            return self.generate_excel(queryset, report_config, filename)
        elif format == 'pdf':
            return self.generate_pdf(queryset, report_config, filename)
```

</Snippet>

Each report is a small piece of configuration: its query, its fields and its column headers. One view renders any of them as CSV, as an Excel workbook through xlsxwriter, or as a PDF through WeasyPrint. A new report is a new dictionary entry, not a new view.

## Results

Inventory Pro covers the core loop for a small inventory: catalog, suppliers, stock in several locations, movement history and printable reports. Its larger result was what it taught me about data modeling and about where an early design starts to strain.

## What I'd do next

Rereading this code more than a year later, I would change three things.

- **Finish the low-stock alerts.** Each product can already flag itself as low on stock (below a fixed 10 units), but the alert panels query fields the models don't define. They should read per-product thresholds from the `StockAlert` model that already exists.
- **Tests for every screen and report.** Two report definitions also reference fields the models don't have: the low-stock report's query is commented out, and the transaction history asks for a creation date and a user. A test that renders each page and report once would have caught all of this.
- **Atomic stock changes.** Recording a transaction and updating a product's quantity should happen inside one database transaction, so a failure can never leave them disagreeing.
